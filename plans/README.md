## Supply-chain check (2026-08-04 keyv/cacheable npm attack)

An npm supply-chain attack on 2026-08-04 (compromised `keyv` maintainer; worm
published poisoned versions of ~444 package names including `keyv`,
`flat-cache`, `file-entry-cache`, `cacheable`) prompted an audit of this repo.
Result: **clean** — no poisoned name@version in any of the three lockfiles or
`node_modules` trees. The app's pinned `keyv@4.5.4`, `flat-cache@4.0.1`, and
`file-entry-cache@8.0.0` (via eslint) predate the attack and cannot resolve to
the poisoned versions (`6.0.0`, `6.1.24`, `11.1.6`).

Before running any plan that installs a new dependency — **only 002 does**
(`expo-secure-store`) — re-run the check:

```bash
node plans/check-poisoned.js plans/poisoned-packages-2026-08-04.tsv
```

`poisoned-packages-2026-08-04.tsv` is a point-in-time snapshot; the list was
still growing on the day of the attack, so refresh it from a current vendor
advisory (Aikido, Socket, Wiz) before trusting a clean result. Also check that
any newly resolved version was published before 2026-08-04
(`npm view <pkg> time --json`). CI and all plan installs use
`--frozen-lockfile`, which pins existing hashes and cannot pull the poisoned
versions.

## Direction — options for the maintainer

Not problems, and not ranked against the bugs above. Each is grounded in
something specific in the repo.

**The app cannot manage the updatable passes it creates.** The server ships a
full management surface (`server/src/index.ts:111-208`) and the MCP server
consumes all six endpoints, but `app/src/lib/api.ts` exposes exactly one
function, `createPass`. The app's answer to "you made an updatable pass" is a
modal telling the user to go use `curl` or an AI agent
(`app/src/app/index.tsx:364-368`). A "My passes" screen is client work against
endpoints that already exist and are already authenticated. The hard half is
rehydrating the editor from a stored spec — the inverse of `createSpec`, which
does not exist yet.

**Nothing the user designs survives a reload.** There is no persistence
anywhere in the app — no `AsyncStorage`, no `SecureStore`, no file-backed
drafts; all pass state lives in 57 `useState` hooks. Losing a half-built poster
event ticket (six artwork slots, semantics, localizations) to an app
backgrounding is the most likely user-facing frustration in the product.
`expo-file-system` is already a dependency and already used for template
artwork. Export/import of the spec JSON would additionally bridge the three
surfaces: design in the app, hand off to an agent, bring it back.

**The full-replacement update API is already forcing workarounds.**
`PUT /api/passes/:serial` demands a complete spec, so the MCP server hand-rolls
a compensating hack: if the caller omits images it silently fetches the stored
spec and splices the old ones back in (`mcp/src/index.ts:193-201`). Meanwhile
the canonical documented use case is a single scalar change — "set my loyalty
card to 450 points" (`INSTRUCTIONS.md:294-296`). A `PATCH` taking a merge-patch
delta would remove the special case and make agent updates cheap. The risk is
real: merge semantics over arrays (`fields.*`, `barcodes`) are genuinely
ambiguous, and getting them wrong silently ships a wrong pass to every
registered device. Do not attempt before plans 001 and 005 land.

**The server discards the answers to the three questions a pass issuer
actually asks.** It already computes per-pass registration counts
(`server/src/db.ts:124-136`), already returns `{sent, failed, pruned}` per push
(`server/src/apns.ts:36-77`), and already receives Apple's device log callbacks
— then `console.log`s them into the void. Persisting push outcomes and device
logs would make "did anyone install it / did the update land / why did Wallet
reject this" answerable without SSH. Retention needs a cap; the data is
device-linked.

**Considered and not recommended: Google Wallet parity.** Every layer is
Apple-shaped by design — `passkit-generator` signing, Apple's web service
protocol as its own router, APNs-only push, a native Swift PassKit sheet, and
385 lines of Apple-specific validation. It would need a parallel spec model, a
JWT issuance path, and a second signing identity: a second product, not a
feature. Recorded so it is visibly considered rather than overlooked.

## Findings considered and rejected

So nobody re-audits these:

- **Unauthenticated device-list route** (`server/src/webService.ts:63-88`) —
  by design. Apple's protocol defines this route without an `ApplePass` header,
  and the comment at line 63 says so. The device library identifier is the
  secret. Rate limiting (plan 004) is the appropriate mitigation, not auth.
- **`ApplePass` token handling** (`server/src/webService.ts:17-29`) — already
  correct. Timing-safe comparison, and a missing serial and a bad token return
  the same 401, so there is no existence oracle. Explicitly left alone.
- **Guessable one-shot download IDs** — not a finding. `randomUUID()` gives 122
  bits, and per-pass auth tokens use `randomBytes(16)`. The unauthenticated
  `GET /api/passes/:id` is required by the Wallet download flow and adequately
  protected by the ID's entropy.
- **SQL injection** — every statement in `server/src/db.ts` is parameterized;
  no string-built SQL exists.
- **Path traversal** — image names are checked against an anchored allowlist
  regex before reaching the filesystem, and `passFilename` strips everything
  outside `[a-zA-Z0-9 _-]` before it reaches `Content-Disposition`.
- **Committed secrets** — none. No `.env`, key, or certificate file is tracked;
  `.gitignore` excludes `*.pem`, `*.p8`, `*.p12`, `*.key`, and `.env*`, and
  `server/src/config.ts` names variables in its failure messages without ever
  logging a value. No rotation is warranted on this basis. (Plan 002 recommends
  rotating `API_TOKEN` for a different reason: bundle inlining.)
- **Prompt-injection content in the repo** — none found. Every subagent checked
  and reported clean.
- **Sharing the nine-line HTTP error-unwrapping between `app/` and `mcp/`** —
  not worth doing. Two copies of nine lines across a React Native bundle and a
  Bun script is cheaper than creating a package to hold them.
- **SQLite `busy_timeout`** — real but not worth its own task; fold it into any
  other change that touches `server/src/db.ts`.
- **`passkit-generator` and `apns2` bus factor** — both single-maintainer and on
  the critical path, both current and actively released. `passkit-generator` is
  effectively irreplaceable here (it is why signing is server-side at all). No
  action; add Renovate or Dependabot so version lag becomes visible rather than
  discovered.
- **React re-render cost in the 945-line editor** — softened by
  `experiments.reactCompiler` in `app/app.json:52`, which auto-memoizes. The
  exposure is the dependency on an experimental flag, not present-day
  performance. Profile before acting; the leverage is in decomposition, not in
  sprinkling `memo`.
